# 실행 가이드: 업무시스템 결재함 부하 테스트 (AWS)

PDF(부하 테스트 강의)의 흐름을 그대로 따라, **AWS에서 병목을 찾고 고치는 과정**을 직접 해보는 실습입니다.

```
① 목표 정하기 → ② 최대 처리량 측정 → ③ 모니터링으로 병목 찾기 → ④ 개선 → ⑤ 다시 측정 (목표까지 반복)
                                                                    + ⑥ 서버 여러 대: 부하 분산 · 장애 테스트
```

## 구성

```
 [내 PC] ──────────────┐
                       ▼
 [부하 발생기 EC2: k6] ──▶ [ALB] ──▶ [앱 서버 EC2 × N: Spring Boot] ──▶ [RDS MySQL: 결재 문서 100만 건]
        │                                                                 ▲
        └──────────── 데이터 넣기 · 인덱스 만들기 (mysql) ──────────────────┘

 [CloudWatch 대시보드]  ALB 요청 수 · 응답시간 p99 · 5xx · 앱 서버 CPU/메모리 · RDS CPU · 부하 발생기 CPU
 [CloudWatch 알람]      P1 긴급(비정상 서버, 5xx) · P2 경고(p99 SLO 초과) · P3 참고(DB CPU 80%) → 메일(선택)
```

- **부하 발생기를 앱 서버와 다른 컴퓨터로 분리**했습니다. 같은 컴퓨터에서 부하를 주면 측정 결과를 믿기 어렵기 때문입니다.
- API는 **"내 결재함" 조회**(95%)와 **결재 상신**(5%)입니다. 직원 1만 명, 결재 문서 100만 건을 가정합니다.
- 결재함 조회 쿼리: `WHERE approver_id = ? ORDER BY created_at DESC LIMIT 20`
- 모든 응답에 `X-Server-Name: app-1` 같은 헤더가 붙어서, k6가 **서버별로 몇 건씩 처리했는지** 셉니다 (부하 분산 확인).
- 대시보드는 **사람이 보고 있을 때만** 쓸모가 있어서, 문제를 먼저 알려주는 **알람**을 등급별로 넣었습니다:

| 등급 | 알람 | 조건 | 의미 |
|---|---|---|---|
| P1 긴급 | `P1-unhealthy-host` | 헬스체크 실패 서버 1대 이상 (1분) | 지금 서버가 죽었다 → 바로 대응 |
| P1 긴급 | `P1-5xx` | 5xx 에러 1분에 10건 초과 | 사용자가 지금 실패를 겪는다 |
| P2 경고 | `P2-p99-slo` | p99 > 0.5초가 3분 연속 | 목표(SLO)를 못 지킨다 → 병목 분석 |
| P3 참고 | `P3-rds-cpu` | DB CPU > 80%가 5분 연속 | 아직 장애는 아니지만 여유가 없다 → 용량 계획 |

- 보안 그룹은 "바로 앞 계층만 허용"(내 PC·부하 발생기 → ALB → 앱 → RDS), IAM 역할은 앱 서버와 부하 발생기를 나눠 **필요한 권한만** 줬습니다.

## 비용 (대략)

앱 서버(t3.small) 1~3대 + 부하 발생기(t3.medium) + RDS(db.t3.micro) + ALB + 알람 4개로, **대략 시간당 0.2~0.3달러**입니다. 실습 전체(3~4시간)에 1~2달러 정도로 예상하지만 정확한 금액은 AWS 요금표를 확인하세요.

> ⚠️ **끝나면 반드시 `terraform destroy`** 로 지우세요. 켜두면 계속 요금이 나옵니다.

## 1. 목표 정하기 (PDF 2단계)

PDF는 "목표 TPS와 Latency를 먼저 정하라"고 합니다. 아래는 **예시 가정**입니다. 발표에서는 "가정"이라고 분명히 말하세요.

- 직원 1만 명이 출근 시간 10분(9:00~9:10) 동안 결재함을 평균 3번 연다
- → 30,000건 ÷ 600초 = **초당 50건**
- → 순간적으로 몰리는 걸 고려해 2배 여유 → **목표: 초당 100건, p99 0.5초 이내, 실패 1% 미만**

k6 스크립트에 이 SLO(p99 0.5초, 실패 1%)가 들어 있어서, 테스트가 끝나면 ✓(달성) / ✗(미달)로 보여줍니다.

## 3. 인프라 만들기 (약 10~15분)

```powershell
cd ..\infra
Copy-Item terraform.tfvars.example terraform.tfvars
Invoke-RestMethod ifconfig.me      # 내 공인 IP 확인
notepad terraform.tfvars           # my_ip = "위에서 나온 IP" 로 수정 (알람 메일을 받으려면 alarm_email 도) 후 저장
terraform init
terraform apply                    # yes 입력
```

RDS 생성에 시간이 가장 오래 걸립니다. 끝나면 이런 값들이 출력됩니다. **메모해두세요.**

| 출력 | 용도 |
|---|---|
| `alb_url` | 브라우저로 열어서 `ok`가 나오면 앱 서버 정상 |
| `cloudwatch_dashboard` | 병목을 찾는 대시보드 (맨 위 ⓪ 칸이 알람 상태) |
| `cloudwatch_alarms` | 알람 목록. 알람을 누르면 "기록" 탭에 울린 시각이 남음 |
| `k6_web_dashboard` | 부하 테스트 중 실시간 그래프 (테스트 중에만 열림) |
| `loadgen_connect` | 부하 발생기 접속 |
| `download_reports` | 리포트를 내 PC로 받는 명령 |

> 나중에 다시 보려면 `terraform output`

`alarm_email`을 적었다면 **"AWS Notification - Subscription Confirmation" 메일의 링크를 눌러야** 알람 메일이 오기 시작합니다.

`alb_url`이 바로 안 열리면 2~3분 기다리세요. 앱 서버가 Java를 설치하고 뜨는 데 시간이 걸립니다.

## 6. 1차 테스트: 조치 전 (약 9분 30초)

```bash
./run-test.sh 1-no-index
```

테스트가 도는 동안 **브라우저에 두 화면**을 열어두세요.
- `k6_web_dashboard`: 요청 수, 응답시간이 실시간으로 그려짐
- `cloudwatch_dashboard`: 계층별 CPU (1분 단위라 조금 늦게 반영됨)

**병목 찾는 법: CloudWatch 대시보드에서 "100%에 붙어 있는 칸"을 찾습니다.**

| 칸 | 100%에 붙어 있으면 |
|---|---|
| ⑦ RDS CPU | DB가 병목 |
| ⑤ 앱 서버 CPU | 앱 서버가 병목 |
| ⑨ 부하 발생기 CPU | 부하 발생기가 한계라 측정을 믿을 수 없음 → `MAX_VUS`를 줄이거나 사양을 올림 |

**예상:** 인덱스가 없으니 ⑦ RDS CPU가 100% 가까이 오르고, 처리량은 낮고, p99는 수 초까지 늘어납니다. 커넥션을 오래 기다리다 ③ 5xx가 생길 수도 있습니다. 예상과 다르게 나와도 괜찮습니다. **그래프가 보여주는 대로 판단하는 게** 이 실습의 목적입니다.

**알람도 보세요:** 인덱스가 없으면 몇 분 안에 ⓪ 칸의 **P2(p99 SLO)**, 이어서 **P3(DB CPU)** 가 빨갛게 바뀔 것입니다. "사람이 대시보드를 안 보고 있어도 알람이 먼저 알려준다"는 증거입니다. 📷 알람이 울린 대시보드를 캡처하세요.

끝나면 터미널에 **리포트 주소(HTML)** 가 나옵니다. 브라우저로 열면 그래프가 정리된 리포트를 볼 수 있습니다.

📷 **캡처할 것:** CloudWatch 대시보드 전체, k6 리포트의 요청 수·응답시간 그래프, 터미널의 ✓/✗ 결과

## 9. 조치 2: 서버 3대로 수평 확장 + 부하 분산 확인

실무처럼 앱 서버를 여러 대로 늘립니다. 2차에서 무엇이 병목이었든, 다음 10단계(장애 테스트)를 하려면 서버가 2대 이상 필요합니다.

내 PC(PowerShell, `infra` 폴더)에서:

```powershell
notepad terraform.tfvars      # app_count = 3 으로 바꾸고 저장
terraform apply               # yes. 앱 서버 2대만 새로 생기고 부하 발생기·DB는 그대로
```

CloudWatch ④에서 **정상 서버 수가 3**이 될 때까지 기다린 뒤(3~5분), 부하 발생기에서:

```bash
./run-test.sh 3-scale-out
```

**확인할 것**
1. 터미널 마지막의 **서버별 처리 건수**: app-1·2·3이 각각 약 33%면 ALB가 고르게 나누고 있는 것
2. ⑤ 앱 서버 CPU: 세 줄이 비슷한 높이로 움직이는지
3. 처리량·p99가 2차보다 나아졌는지. **안 나아졌다면** 병목이 앱 서버가 아니라 DB였다는 뜻입니다(⑦ RDS CPU 확인). 서버를 늘려도 안 빨라지는 것도 중요한 결과예요.

> 2차에서 ⑦ RDS CPU가 100%였다면 `db_instance_class = "db.t3.small"`(수직 확장)도 함께 해볼 수 있습니다. 5~10분 걸리고 그동안 DB가 잠깐 끊깁니다.
>
> 2차에서 아무 칸도 100%가 아니었다면 부하가 부족한 것입니다: `MAX_VUS=400 ./run-test.sh 3b-scale-out-400vu`

📷 **캡처할 것:** 서버별 처리 건수, CloudWatch ⑤ (세 줄), 터미널 ✓/✗

## 10. 장애 테스트: 서버 1대가 갑자기 죽으면? (약 6분)

부하를 주는 중에 앱 서버 1대를 멈추고, **ALB가 몇 초 만에 알아채는지**, **그동안 사용자 요청이 몇 건 실패하는지**를 잽니다. 2~3분 쉬었다가:

```bash
./fail-test.sh 4-failover
```

스크립트가 알아서 이렇게 진행합니다 (손댈 것 없음):

```
정상 부하 60초 → app-1 앱 멈춤 → 1초마다 ALB 판정, 5초마다 긴급 알람 확인 → 180초 뒤 다시 켬 → 정상 복귀 확인
```

끝나면 이런 결과가 나옵니다 (숫자는 예시):

```
 ── 장애 테스트 결과 ──────────────────────
   전체 요청:            40,000건
   실패한 요청:          1,200건 (3.0%)
   ALB가 알아챈 시간:    서버를 멈추고 15.2초 뒤 (요청 보내기 중단)
   사람에게 알람:        서버를 멈추고 95.0초 뒤 (P1-5xx)
   사람에게 알람:        서버를 멈추고 130.0초 뒤 (P1-unhealthy-host)
   실패가 난 구간:       멈춘 뒤 0.1초 ~ 15.0초
   복구(다시 정상 판정): 서버를 켜고 30.5초 뒤
```

**읽는 법**
- 헬스체크 설정은 **10초마다 확인, 2번 연속 실패면 비정상**입니다. 그래서 이론상 **10~20초** 안에 알아채야 합니다. 측정값이 이 안에 들어오는지 보세요.
- 알아채기 전까지는 ALB가 죽은 서버에도 요청을 보내서 **그 몫(약 1/3)이 실패**합니다. 알아챈 뒤에는 실패가 멈춰야 합니다.
- **ALB가 알아챈 시간과 사람에게 알람이 간 시간은 다릅니다.** ALB는 10초마다 직접 확인하지만, CloudWatch 알람은 **1분 단위로 모인 지표**를 보고 판단해서 보통 1~3분 늦습니다. 그래서 "자동 조치(ALB가 빼기)는 초 단위, 사람 호출(알람)은 분 단위"라는 구조가 됩니다. 이 차이를 숫자로 보여주는 게 이 테스트의 핵심입니다.
- 수업 실습(aws-02)은 30초 × 2번이라 탐지가 최대 60초였습니다. **"탐지 간격을 줄이면 사용자 피해가 줄어든다"**를 숫자로 보여주는 장면입니다.
- 남은 2대만으로 부하를 버텼는지(p99, ⑤ CPU)도 확인하세요.

📷 **캡처할 것:** 터미널 결과 표와 5초 단위 실패 그래프, k6 리포트의 실패(http_req_failed) 그래프, CloudWatch ③ 5xx · ④ 정상/비정상 서버 수

> 옵션: `DOWN_SECONDS=240 VUS=80 ./fail-test.sh 4b-failover` (멈춰 둘 시간, 부하 크기)
>
> 장애 테스트는 **6분** 걸립니다. 알람은 1분 단위라 울릴 시간을 주려고 서버를 3분간 멈춰 둡니다.

## 문제 해결

| 증상 | 해결 |
|---|---|
| `terraform apply`에서 `approval-app.jar` 파일을 못 찾음 | 2단계(앱 빌드)를 먼저 하세요 |
| `apply`에서 인스턴스 유형이 허용되지 않는다는 오류 (프리 플랜 계정) | `terraform.tfvars`에 `loadgen_instance_type = "t3.small"` 추가 후 다시 `apply`. 그래도 안 되면 계정을 유료 플랜으로 전환해야 함 |
| `alb_url`이 안 열림 (시간 초과) | `my_ip`가 지금 내 IP와 같은지 확인. 와이파이가 바뀌면 IP도 바뀜 → tfvars 수정 후 `terraform apply` |
| `alb_url`이 502/503 | 앱 서버가 아직 뜨는 중. 3~5분 기다리기. 계속이면 아래 "앱 로그 보기" |
| k6 웹 대시보드가 안 열림 | 테스트가 실행 중일 때만 열립니다. 내 IP가 바뀌었는지도 확인 |
| `seed.sh`에서 접속 오류 | 1~2분 뒤 다시. RDS가 막 생성된 직후일 수 있음 |
| `bad interpreter: ^M` | 스크립트 줄바꿈이 Windows 형식으로 바뀐 것. 압축을 다시 풀어서 사용 |
| `fail-test.sh`: 정상 서버가 1대라고 나옴 | 9단계(`app_count = 3` → `apply`)를 먼저. 새 서버가 뜨는 데 3~5분 |
| `fail-test.sh`: AccessDenied (ssm:SendCommand) | 앱 서버를 늘린 뒤 `terraform apply`가 끝났는지 확인 (권한이 서버 목록을 따라 바뀜) |
| `fail-test.sh`: "이미 울리고 있는 긴급 알람" | 이전 테스트의 알람이 아직 OK로 안 돌아온 것. 2~3분 뒤 다시 |
| 알람 메일이 안 옴 | 구독 확인 메일의 링크를 눌렀는지 확인. 스팸함도 확인 |
| `fail-test.sh`: 명령 결과를 못 받음 | 앱 서버의 Session Manager 연결이 아직 준비 안 됨. 서버가 뜨고 몇 분 뒤 다시 |

**앱 로그 보기:** EC2 콘솔 → `approval-app-1` → 연결 → Session Manager → 연결 후

```bash
sudo journalctl -u approval-app -n 100 --no-pager
```
